# 012: 画素数は表示サイズで決める

## Status

Proposed

## Context

キャッシュに入る画像の画素数を、誰も決めていなかった。

| ソース | 保存される画素数 | 決めたのは |
|---|---|---|
| SMB 画像 / ZIP | スキャン元のまま | 元データ |
| Pixiv (一覧) | サーバーが返すまま (`square1200` なら 1200x1200) | Pixiv |
| Pixiv (ページ) | `regularUrl` = 長辺 1200px 程度 | Pixiv |
| サムネイル (生成する場合) | 長辺 600px | 定数 |
| PDF ページ | ページ寸法 x 2 | 定数 |

一方、表示する側の寸法は端末で決まっている。8 インチのタブレット
(物理 800x1340、density 180、dpr 1.125) を実測すると:

| | 物理 px |
|---|---|
| グリッドのタイル (縦画面 5 列) | **155** |
| グリッドのタイル (横画面 5 列) | 263 |
| フル画面 | **800x1340** |

つまり 155px のタイルに 600px や 1200px の画像を置き、800x1122 で見る PDF を
2156x3022 で描いていた。**縦横で 4〜7 倍、画素数で 15〜50 倍の過剰**。

### 過剰が実際に費用として現れる 3 か所

1. **PDF のページ送りが 1 枚 2.6 秒**。うち 9 割が PNG エンコードで、コストは
   画素数にほぼ比例する。実測は `notes/` の調査記録 (非公開) にある
2. **デコード後のメモリ**。タイルは `Image.memory(d, fit: BoxFit.cover)` で
   `cacheWidth` を渡していないので、保存された画素数のままデコードされる。
   1200x1200 は RGBA で 5.76MB、Flutter の `ImageCache` は既定 100MB なので
   **17 枚で満杯**。縦画面 1 画面が 40 タイルなので、スクロール中は
   デコードとその破棄を繰り返している
3. **L2 の容量**。PDF は 1 ページ 2〜3MB、124 ページの本で 1 冊 370MB

### なぜ今まで気づかなかったか

判断基準が**バイト数**だったから。`resizeToThumbnail` は 400KB 以下を無加工で
通す。これは「小さい JPEG を PNG に変換すると逆に大きくなる」への対処で、
判断基準としては正しくない — **300KB の JPEG が 3000x2000 (600 万画素) は普通**。
バイト数は画素数の代理にならない。

## Decision

**画素数は、そのデータが表示される寸法から決める。** サムネイルもページも同じ規則。

### 1. サムネイルの目標画素数は端末ごとに 1 つ

グリッドのタイル寸法を**向きに依存しない 1 つの数**にする:

```
基準タイル(dp) = (shortestSide - padding*2 - spacing*(列数-1)) / 縦画面の列数
目標画素数     = 基準タイル(dp) * devicePixelRatio
```

`shortestSide` は回転しても変わらないので、この数は向きで変わらない。
端末の大きさには適応する (固定 dp 定数だと狭い端末で 2 列になってしまう)。

**縦画面の列数は既定 5。** タブレットではちょうどよく、スマホでは小さいので、
将来は設定から変えられるようにする (入れ物が無いので別タスク)。実装では
1 つの値として持ち、参照は 1 か所の関数を通す。

### 2. 横画面は列を増やす。タイルは大きくしない

従来は 5 列固定で、横画面ではタイルが 1.7 倍に伸びていた。これでは
「保存すべき画素数」が向きで変わり、L2 に入れる数を 1 つに決められない。

```
列数 = 基準タイルが入るだけ入れる
余り = 列間の空きに配る
```

実測の端末なら横画面は **8 列・spacing 12dp** で基準タイルちょうどになる。

### 3. リサイズの判断は画素数で行う

バイト基準 (400KB) を廃止する。**目標画素数を超えていれば縮める。**
155px まで縮めれば PNG でも数十 KB なので、「PNG にすると大きくなる」という
元の懸念は自然に消える。Pixiv も例外にしない (今は素通し)。

### 4. 表示側も画素数を指定する

保存側を直しても、既存のエントリと元データそのままのソースは残る。
`Image.memory` に `cacheWidth` を渡す。**グリッドのタイルだけでなくビューアも** —
3000x2000 のスキャンはデコード後 24MB で、4 ページ先読みすると
`ImageCache` の既定 100MB を超える。

### 5. PDF ページは「画面に収めたときの大きい方」

縦画面と横画面それぞれにページを収めたときの寸法を出し、大きいほうを採る。
実測の端末・実測のページ (1078x1511pt) なら:

| | 収まる寸法 | 画素数 |
|---|---|---|
| 縦画面 (800x1340) | 800x1122 | 90 万 |
| 横画面 (1340x800) | 570x800 | 46 万 |
| **採用** | **800x1122** | **90 万** |
| 従来 (x2) | 2156x3022 | 651 万 |

**7.2 分の 1。**

### 6. ズームは「大きく作っておく」ではなく「聞かれたら取り直す」で応える

これが上を成立させる前提。従来の x2 は結果的にズームの余裕になっていたので、
画面ぴったりにすると拡大でぼやける。**それを許容し、必要になったら取り直す。**

| ソース | ズーム時にすること (将来) |
|---|---|
| Pixiv | `originalUrl` を取り直す (今は `regularUrl` 固定) |
| PDF | 可視領域を高倍率で再描画する |
| SMB / ZIP | 元が既に大きいので不要 |

**この節が ADR の中で一番消えやすく、一番消えてはいけない。** 「PDF のズームが
ぼやける」を見た人が `scale` を 2.0 に戻すのは自然な動きで、そうすると
1 枚 2.6 秒が黙って戻る。定数ではなく方針として書いてある理由がこれ。

## Alternatives

### x2 を小さい定数に変える (x1.4 など)

最初に検討した案。他ソースのズーム余裕 (Pixiv の regular で 1.1〜1.5 倍) に
合わせる、という理屈は立つ。**却下した理由は、定数を別の定数に替えても
「なぜその数か」が説明できないから。** x2 が壊れていたのは値が大きすぎたから
ではなく、**ページ枠が A4 だと仮定していた**から (A4 なら x2 は 1600px の画面に
ちょうど合う。実測のページ枠は A4 の 1.8 倍なので外れた)。表示サイズから
逆算すれば、どんなページ枠でも正しい。

### 目標画素数を固定の dp 定数にする

`基準タイル = 138dp` のように決め打ちする案。**狭い端末で 2 列になってしまう**。
`shortestSide / 列数` なら端末に適応し、かつ向きに依存しない。

### 横画面でもタイルを伸ばす (現状維持)

保存すべき画素数が向きで 1.7 倍変わり、L2 に入れる数を 1 つに決められない。
「向きを変えたらサムネイルが作り直される」か「どちらかの向きで粗い」の
どちらかになる。

### L2 のサムネイルを版付きキーで作り直す

目標画素数が変わると既存エントリは「大きいだけ」になる。作り直しを強制する案も
あるが、**表示は正常**なので放置し、LRU に任せる。作り直したいときは L2 クリア
(索引に無い孤児ファイルも消える) か、「サムネイルも作り直すリロード」を使う。

## Consequences

- **Good**: PDF のページ送りが 2.6 秒 → 0.4 秒前後の見込み。ページ 3MB → 0.5MB
- **Good**: デコード後のメモリが桁で減る。1200x1200 (5.76MB) → 155x155 (0.096MB) は
  **60 分の 1**。`ImageCache` に 17 枚しか入らなかったものが 1000 枚入る。
  スクロールのガタつきに効く可能性が高い (ADR 011 の調査では
  ページングと索引書き出しが主因と分かったが、これは独立した別の原因)
- **Good**: 判断基準が「バイト数」から「画素数」になり、なぜその数かを言える
- **Good**: タイル寸法が向きで変わらないので、目に見える一貫性も上がる
- **Bad**: ズームがぼやける。上の 6 のとおり承知の上で、対処は別タスク
- **Bad**: Pixiv のサムネイルに再エンコードが要る (今は素通し)。CPU を 1 回払って
  メモリを 60 分の 1 にする取引
- **Bad**: 列数が幅の関数になるので、幅の出どころが 2 種類あるのが問題になる。
  グリッドは `constraints.maxWidth`、先読みの帯は画面幅を見ている。境界付近で
  列数が食い違うと帯が 1 行ずれる。**見えているタイルは自分で要求する
  (ADR 011) ので影響は先読みの範囲だけ**。別タスクで揃える
- **Bad**: 既存の L2 (実測 3.71GB) は古い画素数のまま残る。放置する
