# ADR 011: サムネイルをプル型にする (画面が要求し、優先度つきで応える)

## Status

Accepted (2026-08-02 実装完了。段階 0〜4。設計と不変条件は
[docs/thumbnails/design.md](../thumbnails/design.md)、構成は
[thumbnail_architecture.md](../thumbnail_architecture.md))

## Context

現行のサムネイル供給はプッシュ型: `ThumbnailLoader` が「リスト先頭からどこまで
配ったか」の水位 (`_loadedCount`) を持ち、描画が水位を越えるたび次の 30 件
(5 列 × 6 行) を配る。配った答えはセッションが `_thumbnailResults` に貯める。

この形の帰結が連鎖している:

1. 貯めたものが**スクロールした量だけ**際限なく増える (実測 591 件 ≈ 十数 MB)
2. だからビューを離れるとき `detach()` で**全部捨てる** (ADR 007 決定 5)
3. 全部捨てたから `attach()` で**全部読み直す**。実測 (2026-08-02、実機):
   **591 件を先頭から直列読みして 10.5 秒。うちディスク読みが 10.49 秒**、
   1 件ごとの再描画は合計 8ms で無害。読む順がリスト先頭からなので、
   見ている場所のタイルが最後に埋まる
4. 「配り済み」の帳簿 (`_resultIds`) と「画面が描けるか」が別の質問なのに、
   帳簿しか見ない。キャッシュを消すと「答え済みだが画面は空」になり、
   全面スピナーで固まるバグを実際に踏んだ (`resumeMissingThumbnails` は
   その対症)

計測で否定されたことも記録する: 「戻ると再ダウンロードしているのでは」は
**誤り** (戻った後のネットワーク取得はゼロ)。「1 件ごとの setState が重い」も
**誤り** (8ms)。遅さの正体は**持っているものを 591 回直列に読み直すこと**自体。

## Decision

プッシュ型をやめ、**プル型**にする。原則は 1 つ:
**コストを「今まで見た量」ではなく「今見えている量」に比例させる**。

### 1. 要求は描画が生む

タイルが描かれるときにプールを引き、無ければ要求を積んでプレースホルダを
描く。「配り済みの帳簿」は持たない — **描かれる = 要求される**なので、
キャッシュが消えていようが読み残しがあろうが、見えたものは必ず埋まる。
永久スピナーの類が構造的に起きなくなる。

### 2. デコード済みバイトはアプリ全体で 1 つの上限つきプールに

セッションごとの無制限マップをやめ、バイト数上限つき LRU (`ThumbnailPool`) に
置き換える。上限があるので「離れるとき全部捨てる」理由が消え、戻ったときの
大半はメモリヒットで即描画。あふれた分は LRU が押し出す。

アプリ全体で 1 つにするのは、セッションごとだとタブの数だけ上限が増えて
detach 問題が再発するのと、同じ作品が複数タブに出るとき共有が効くため。

### 3. 優先度はビューポートからの距離。取得範囲は可視 + 前後 1 画面

要求の優先順は「見えている > スクロール方向の次の 1 画面 > 手前の 1 画面」。
帯の幅は実画面から計算する (5 列 × ビューポート高さ ÷ 行の高さ)。固定 30 件の
水位方式と違い、回転・画面サイズに追従する。帯の外は**そもそも取得しない** —
速いスクロールで通り過ぎた分のネットワーク取得が消える。

### 4. レーンを分けたスケジューラが応える

`ThumbnailScheduler` が 1 本の優先度つきキューを持ち、ディスク読み (並列 8) /
ネットワーク (並列 5、現行踏襲) / 動画 (直列、現行踏襲) のレーンで消化する。
ビューポートが動いたら並べ直し、帯から外れた要求は捨てる (描かれれば再要求
される)。同じ id の重複要求はまとめる。

## 採らなかった案

- **`attach()` の並列化 + anchor 起点だけの修正** — 10 秒は消えるが、
  「全捨て・全読み直し・帳簿」という構造は残る。帳簿と画面の食い違い系の
  バグの土壌が残り、次の症状で再修理になる
- **セッションごとのプール** — 上限がタブ数倍になり、全捨ての動機が再発する
- **可視分だけ読んで残りは帳簿に従う (折衷)** — 帳簿が「答え済み」と言う
  項目は二度と埋まらないため、帳簿を直さない限り成立しない。直すなら
  プル型まで行くのが同じ手間
- **L1 (10 枚、フル画像と共用) をサムネイル用に拡張** — プールが実質その
  役割を果たすので不要。むしろサムネイルを L1 に書くのをやめる

## Consequences

- `detach`/`attach` の全捨て・全読み直し、`_resultIds`、配布水位、
  `needsBatchFor`、`resumeMissingThumbnails`、`retryInterrupted` が**削除**できる
- 失敗の記録 (`notSupported` はビューア表示後だけ再試行) と Pixiv サムネイル
  URL 陳腐化時の取り直し、動画再生前のキャンセルは、プール/スケジューラに
  引き継ぐ (挙動不変)
- 計測ログは同じ形で残す (要求波ごとに「N 件 = プール M + ディスク K +
  ネット J、X ms」)。今回の調査はこのログが無ければ推測で直していた
- タブを移った直後の再描画 (ディスク/ネット読み) は許容する (2026-08-02 に
  ユーザーと合意)。プールに残っていれば即、無ければ優先度順に埋まる
- リスク: タイルごとの通知 (`ValueListenable`) への移行で再描画の粒度が
  変わる。特性テストを先に敷いて挙動を固定してから進める (design.md 段階 0)

## 実装で変えた判断 (2026-08-02)

- **プールの置き場**: 「アプリ全体で 1 つを引数で配る」としていたが、セッション
  生成箇所が lib と test で 40 箇所あり、その全部が既に `CacheManager` を
  受け取っていた。プールは L1 がサムネイルに対して果たせなくなった役割の
  引き継ぎで、寿命も注入点も CacheManager と一致する。`CacheManager.thumbnails`
  として持たせた (クラスは独立、`CacheManager.get` は触らない)
- **スケジューラは場所ごとに 1 つ**: ADR ではアプリで 1 つとしたが、**ビューを
  持つのはアクティブなタブだけ**なので、同時に動くのは実質 1 つ。場所ごとにすると
  provider がその場にあり、配線が要らない。「アクティブなタブだけが描く」が
  崩れたら見直す
- **I2 の訂正**: 「notSupported はビューア表示後に再試行する」は**動いていなかった**
  (`retryUnsupportedThumbnails` の呼び出し元が ADR 010 のタブ化で消えていた)。
  不変条件は実際に成り立っている「描画のたびに再試行しない」に直した。
  ビューア往復での再試行を復活させるかは未決 (design.md「残る検討」)

## この調査で分かった、より大きな 2 つ (2026-08-02)

プル化しても「未取得の一覧をスクロールすると 3〜5 行で止まる」が残り、計測で
**サムネイル供給とは別の 2 つ**が主因と判明した。どちらも ADR 011 の範囲外だが、
同じ症状の一部だったので記録する。

1. **L2 索引の全書き出し** — `DiskCache` が 5 操作ごと (読み取り含む) に索引を
   まるごと JSON 化していた。1 万エントリで 90ms、150ms ごと。時間で間引き +
   読み取りでは予約しない + 背面移行時に確実に書く + 形式を小さくする、で対処
2. **ページ先読みが 200px** — 次ページ要求が終端の 1.3 行手前。Pixiv の応答は
   1〜2 秒なので、読者が終端に張り付いて止まっていた。「下に 3 画面ぶんの
   滑走路を保つ」に変更。**プル化していなければこの変更はできなかった** —
   プッシュ型ではページ先読みがそのままサムネイル先読みになっていた

フレーム時間の計測 (`frame: build Xms + raster Yms`) が決め手だった。30 秒の
スクロールで 32ms 超が 4 フレームしかなく、「描画が重い」という筋を潰せた。
