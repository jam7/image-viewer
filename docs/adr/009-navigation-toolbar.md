# ADR 009: 戻る・進むはツールバーの明示ボタンにする

## Status

Accepted (2026-07-26)

## Context

[ADR 008](008-tab-identity-and-history.md) でタブ内履歴を導入し、戻る操作を
5 経路 (ESC / Backspace / 横スワイプ / マウス戻る / システム戻る) に統一した。
残っていた課題が 2 つ:

1. **進む (forward)**: `GalleryTab.forward()` は実装・テスト済みだが、割り当てる
   入力が無く未配線のまま
2. **履歴ジャンプ**: 「戻るボタン長押しで履歴一覧」を構想していた

これらをジェスチャや長押しに割り当てる前提が、Android 15 で崩れた:

- **戻るボタンが存在しない**。ナビゲーションはジェスチャのみで、
  「戻るボタンの長押し」は原理的に不可能
- **画面端は OS のものになった**。エッジスワイプは predictive back
  (辺が波打つプレビューアニメーション付きの戻り) に取られていて、
  アプリが左右エッジに独自ジェスチャを置く余地がない
- アプリ内履歴を歩くために `PopScope` で戻りを横取りすると、predictive back の
  プレビューは表示されない。これはアプリ内ナビゲーションを持つアプリ共通の
  トレードオフ (Chrome も同じ) で、受け入れる

## Decision

**ブラウザと同じく、ナビゲーションは画面上の明示的な UI にする。**
ギャラリーのヘッダーを 2 行構成にする:

```
1 行目:  [タブ][タブ][タブ]…  [+]          ← 既存のタブストリップ
2 行目:  ←  →  [ 場所の表示 / 検索 ]  ☰    ← 新設のツールバー
```

- **← / →** はアクティブタブの履歴を歩く。先頭 / 末尾では灰色になり、何もしない
- **場所の窓**はアドレスバーと検索窓を兼ねる (詳細は
  [design.md](../virtualized_gallery/design.md) のツールバー節)
- **☰** は「今のタブの中の行き先 + アプリ操作」。Pixiv ならセクション
  (トップ / ブックマーク) が上段に載り、下段に再読み込み・設定。
  `+` は「新しいタブを開く」専用のまま
- **両行ともスクロールで隠れ、上スクロールで戻る**。タブレット横画面では
  サムネイル 2.7 行分しか見えておらず、常設 2 行は許容できないため
- システム戻る (ジェスチャ) も履歴を 1 つ戻る。先頭では**飲み込まずに OS へ渡す**
  (Android ならアプリが背面へ)。ツールバーの ← はそれと同じ操作の可視化

### 採らなかった案

- **エッジスワイプで進む/戻る**: OS が画面端を所有するため成立しない (上記)
- **戻る長押しで履歴一覧**: 長押しする対象のボタンが無い。履歴一覧は将来
  ← の長押し (ツールバー上のボタンなら長押しできる) か ☰ 内に置ける。
  今回は配線しない
- **Chrome の N 窓 (タブ数ボタン)**: スマホ版 Chrome にあるのはタブストリップが
  無いからで、ストリップがある本アプリでは役割が被る。ストリップが溢れて
  一覧性が落ちてから検討する

## Consequences

- **Good**: 進むがようやく家を得る。プラットフォーム差 (Android 15 に戻るボタンが
  無い、iOS にジェスチャの流儀がある) に依存しない、常に見えて説明不要のナビになる
- **Good**: アドレスバーの導入で「リンクからタブを作る」(ADR 008 の構想) が完成する
- **Bad**: 縦 48dp 程度を消費する。スクロール自動隠しで緩和するが、
  隠れている間は ← → も使えない (システム戻るは常に効くので致命ではない)
- **Note**: ビューアと動画プレーヤーは従来どおり Navigator のルート
  (ADR 008 のスコープ外) なので、このツールバーはビューア内には出ない

## 追記 (2026-07-26): 戻るでタブを閉じるのをやめる

[ADR 008 の追記](008-tab-identity-and-history.md) は「履歴の先頭で戻るとタブを
閉じ、最後の 1 つならホームに置き換える」とした。**同日中に、実際に使ってみて
取り消した。**

理由は、**戻るが取り消し不能な破壊を兼ねてしまう**こと。履歴はこのツールバーで
初めてユーザーから見えるものになったのに、その入口の 1 つがそれを捨てる。しかも:

- ← の連打、predictive back の二重入力は現実に起きる
- 閉じたタブを開き直す機能が無いので、事故ると復旧できない
- 一方、閉じる操作はタブの `x` として常時見えている

**破壊はコストの高い操作にだけ割り当てる**という原則からすると割り当てが逆だった。
最初の設計は「戻るが常に何かをする」ことを優先して、失うものの大きさを軽く見ていた。

改めた規則:

| 入口 | 履歴あり | 履歴の先頭 |
|---|---|---|
| ← / Escape / Backspace / マウス戻る / 横スワイプ | 1 つ戻る | **何もしない** (← は灰色) |
| システムのジェスチャ戻る | 1 つ戻る | **OS へ渡す** (アプリが背面へ) |
| タブを閉じる | — | タブの `x` のみ |

`PopScope(canPop: !tab.canGoBack)` の 1 行で表せる。副産物として、先頭では
predictive back のプレビューが再び動く (`canPop: false` では飲み込まれていた)。

### Chrome との対応

Chrome は 2 層になっている。デスクトップのツールバー ← は先頭で灰色。モバイルの
システム戻るは、リンクから生まれた子タブなら閉じて親タブへ戻り、`+` から開いた
独立タブなら他にタブがあってもアプリが背面へ行く。つまり「複数タブがあれば別タブへ
戻る」という挙動は Chrome にも無い。

子タブの特別扱いは**閉じる動作と一体**なので、それをやめた本アプリでは選択肢に
入らない。加えて本アプリはタブストリップが常時見えている (モバイル Chrome は
N 窓の裏) ので、閉じるを戻るに兼ねさせる必要が薄い。

### 消えたもの

判断の分岐そのものが無くなったので、2C-1 で入れた配管もほとんど不要になった:

- ホスト側の `_exitTab` / `_isLastHome`、`onExitTab` の 4 ボディ配線
- `onBack` の 4 ボディ配線 — 分岐が無ければホストもボディも `tab.back()` を
  呼ぶだけで、判断が 2 箇所に分かれる問題自体が消える
- `HomeGalleryBody` の PopScope 特例 — 全ボディが同じ規則になった
- 「本番は通らないがテストだけ通る」フォールバック経路

「最後の 1 つはホームに置き換える」も廃止した。行き先を失う経路がもう無い。

### 見送った案: タブ間の訪問履歴

タブを複数開いて 3 番目で先頭まで戻ると、「さっきまで 1 番目にいた」は無視して
アプリが背面へ行く。これを拾うには「どのタブにいたか」の第 2 の履歴が要るが、
タブ内履歴と別次元の履歴が並ぶと、戻るがどちらを辿るのか予測しづらくなる。
必要になってから足す (後付けできる)。
