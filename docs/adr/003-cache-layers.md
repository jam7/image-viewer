# 003: 3層キャッシュアーキテクチャ

## Status

Accepted

## Context

リモートサーバーから画像をストリーミング表示するアプリで、レスポンス速度・メモリ消費・ディスク使用量・ユーザー意図 (ダウンロード) のバランスを取る必要がある。

## Decision

3層キャッシュ + お気に入り (メタデータのみ) の構成を採用。

| 層 | 保存先 | 排出 | 用途 |
|---|---|---|---|
| L1 | メモリ | LRU 自動 (~10枚) | 現在表示中 + 近傍ページ |
| L2 | ディスク | LRU 自動 (500MB〜5GB) | セッション中のキャッシュ |
| L3 | ディスク | 手動トグル | ユーザーが明示的にDLした作品 |
| お気に入り | JSON | 手動トグル | URL + メタデータのみ (画像なし) |

`CacheManager.get(key)` が L1 → L2 → L3 の順に検索し、ヒット時は上位層に昇格。

## Alternatives

### 2層 (メモリ + ディスク)

- L3 がないとユーザーのダウンロード意図を表現できない。LRU で意図的に保存した画像が消える

### ディスクキャッシュのみ

- メモリキャッシュがないとページめくりのたびにディスク I/O が走る。特にスワイプ時のラグが大きい

## Consequences

- **Good**: L1 でページめくりが即座。L2 で同一セッション中の再表示がディスクから即座。L3 でユーザーの保存意図を永続化
- **Good**: 各層が独立したポリシーで排出。L2 は LRU で自動管理、L3 はユーザー操作のみ
- **Good**: キー命名 (`thumb:` / `full:`) で同一アイテムのサムネイルとフル画像を分離
- **Bad**: L2 のサイズ管理 (atomic write、メタデータ JSON) の実装が必要
- **Bad**: L3 の作品単位ダウンロード (複数ページ、ZIP、PDF) で種別ごとの保存ロジックが必要

## 実装の共通化 (2026-08-02 追記)

層の分け方は上のまま。その下で **L2 と L3 は同じ実装 `KeyedFileStore`
(`lib/services/cache/keyed_file_store.dart`) を継承する**ことにした。

両者が持っているものは同じ — キーの SHA-256 を名前にしたファイルのディレクトリ、
`CacheEntryMeta` の索引 (`_metadata.json`、tmp へ書いて rename)、合計サイズ。
**違うのは 2 つのポリシーだけ**で、どちらもコンストラクタ引数にした:

| | L2 (`DiskCache`) | L3 (`DownloadStore`) |
|---|---|---|
| `maxSizeBytes` | 上限あり。超えたら最終アクセスが古い順に捨てる | `unlimited` |
| `indexDelay` | 5 秒。まとめて 1 回書く | null。変更を呼び出しが返る前に書く |

`indexDelay` を違えるのは意図的。L2 がこの窓で失うのはキャッシュ (また取れる) だが、
L3 が失うのは「ユーザーが取っておくと言った」記録で、ファイルだけ残って誰も知らない
孤児になる。L3 の書き込みは DL 操作のときだけなので、遅延させる利益もない。

### なぜ共通化したか

**同じものを 2 回書いた結果、片方にしか入らなかった修正が 3 つあった**:

- 索引書き出しの再入ガード (`_isFlushing` / `_needsFlush`) が L2 のみ
- 消えたファイルの自己修復で、L2 は合計サイズも直すが L3 は直さない
  (テストが `(current behavior)` と書いて固定していた)
- 索引書き出しの遅延化 (90ms がスクロールを止めていた対処) が L2 のみ。
  これは 3 つの中で唯一「L3 では違ってよい」もので、上表のとおり引数として残した

つまり 3 つのうち 2 つは差ではなく取りこぼしだった。共通化で両方に入る。

### 帰結

- **Good**: 排出方針以外の修正が自動的に両層に効く
- **Good**: L3 も読み取りでアクセス時刻を更新するようになった (索引を汚すだけで
  書き出しは起こさない)。将来 L3 に上限を付けるなら LRU がそのまま使える
- **Bad**: 継承なので、基底の変更が両層に効く。効かせたいから継承したのだが、
  ポリシーの差が 3 つ 4 つに増えるようなら合成へ組み替える判断がいる
